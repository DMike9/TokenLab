# TokenLab: start here

This is the actual project source, not a prompt to generate a project. Open the folder containing `package.json` in VS Code. You do not need AWS, Docker, Python, a database or a Gemini key for the core lab.

**Build status:** The post Phase 2 hardening gate is documented in [HARDENING-REPORT](docs/HARDENING-REPORT.md). Current commands, counts and verification limits are in [BUILD-STATUS](docs/BUILD-STATUS.md). Core algorithms and browser embeddings work locally; live Gemini and deployment remain unverified.

## 1. Open the project

Extract `TokenLab.zip`. In VS Code choose **File → Open Folder** and select **TokenLab**, the folder with `package.json`. Do not open only the ZIP or a parent folder.

Choose **Terminal → New Terminal** and check:

```powershell
node --version
git --version
```

Node must be **22.12 or newer**; Node 22 or 24 LTS is the intended environment. If Node is missing, install an LTS release from the official Node.js site, then completely restart VS Code. Node is the runtime, not another hosting platform. Existing Git and VS Code are enough for the rest of the workflow.

## 2. Let the coding agent perform the local verification

Open **Codex inside VS Code**, sign in when prompted, and use the exact prompt in `docs/AI-HANDOFF.md`. This directs the agent to install dependencies, fix real compilation/integration issues, run the test suite and inspect the browser. Grant access to this project and approve package installation commands; do not grant unnecessary access to unrelated folders.

The workspace now includes a real `package-lock.json` generated by successful installation and verified with `npm ci`. Use `npm ci` for clean installs, and `npm install` when intentionally changing dependencies.

You can run the same commands yourself:

```powershell
npm install
npm run verify
npm run check:core
npx playwright install chromium
npm run test:e2e
npm run dev
```

`npm run verify` includes TypeScript checking, Vitest, the gateway mock tests and the production build. Browser tests are separate. Do not publish while a verification command is failing. Run `npm audit`, investigate its output, and do not blindly run `npm audit fix --force`.

When Vite displays its local address, open it in your browser. The default is `http://127.0.0.1:5173`.

**Windows PowerShell:** If you see “npm.ps1 cannot be loaded because running scripts is disabled,” use `npm.cmd` and `npx.cmd` instead of `npm` and `npx`. You do not need to weaken the machine-wide execution policy. If port 5173 is occupied, stop the old development server with Ctrl+C; the configuration intentionally does not silently change ports.

## 3. Try the first demonstration

Load **Same scores, different math**, click **Analyze prompt**, then **Compare math**. Inspect the actual counts and expand **Sigmoid vs Softmax** for chunk decisions. **More research experiments** offers the focused pair and an independent budget ladder. Open **Research** to adjust task focus, weights, cutoff and optional local embeddings. See [the math experiment note](docs/MATH-EXPERIMENTS.md) for formulas and measured examples.

Load **The negation trap**. Confirm that `NOT`, the prohibition, and the required output survive. Set an aggressive target and observe an honest **budget unmet** result when protection makes the target infeasible.

Click **Download / enable local embeddings** to add measured cosine similarity and the Pareto view. This step downloads public model/runtime files. It does not send your prompt for inference. Downloads and real inference passed in the tested local Chromium environment; a new browser still needs network access and sufficient memory. Failed model loading produces an error, not a made-up score. Older rows do not acquire scores retroactively; run new experiments after enabling the model.

Load **Structured JSON** to see a deliberate limitation: this version protects valid JSON verbatim. It does not pretend that arbitrarily deleting JSON fields is safe.

## 4. Publish the repository from VS Code

First confirm that `npm run verify` and the browser checks pass and review `docs/RELEASE-CHECKLIST.md`.

In **Source Control** (`Ctrl+Shift+G`), initialize the repository if required. Stage the source files and the newly generated lockfile. Commit with a message such as `Initial TokenLab experimental research build`. Choose **Publish to GitHub** and select your personal **DMike9** account, not a company organization. Choose a repository name such as `tokenlab` and public visibility when you are ready to share it. The exact button wording can vary by VS Code state.

Check the staged changes: `.env.local`, credentials, `node_modules`, `dist`, and browser caches must NOT be included. The `.gitignore` already excludes them. If Git asks for an author, set your preferred name and GitHub email for this repository, not a different company's identity.

Publishing instructions describe a human-operated workflow; this guide does not establish the current remote repository or deployment state.

## 5. Put the keyless application on GitHub Pages

The repository includes a manually triggered Pages workflow. In GitHub open **Settings → Pages → Build and deployment → Source: GitHub Actions**. Then open **Actions → Deploy TokenLab to Pages → Run workflow**.

The workflow installs dependencies, runs verification, builds, and deploys `dist`. GitHub will show the actual site URL after successful deployment. Do not infer success from the workflow file existing. Availability depends on your account/repository settings. The deployment uses a relative Vite base so a repository subpath works.

GitHub Pages serves the browser app only. **It does not run the Gemini gateway.** Public visitors can use the local algorithms and download the public embedding model. The Gemini Arena is for your local setup until a separately authenticated, budget-controlled backend is designed. Never publish the local development proxy as an unrestricted public service.

## 6. Optional: connect Gemini locally

Do this only after the keyless application works. Keep the key out of chat, source code, screenshots, exports and GitHub.

In the VS Code terminal:

```powershell
Copy-Item .env.example .env.local
```

Open `.env.local` yourself and set `GEMINI_API_KEY` to your key. `GEMINI_MODEL` names the model you can access. The example uses `gemini-3.8-flash`, based on the Google documentation reviewed September 8, 2026; available models and your account permissions can differ. No model/key combination was tested against Google during authoring.

Google's September 2026 documentation says standard API keys must migrate to auth keys. If an older key is rejected, review its type in AI Studio rather than posting it to a coding agent. See the primary-source links in `docs/RESEARCH.md`.

Keep `npm run dev` running. Open a **second terminal** and run:

```powershell
npm run gemini
```

In the application, run a compression experiment, expand **Gemini Arena**, authorize sending the prompt pair, click **Check local gateway**, and then **Compare original vs compressed**. Each comparison makes up to two generation calls and can incur charges. The optional reference answer is not sent to the model.

Gemini token usage is obtained from Google's returned usage metadata, not from the GPT BPE encoding. A single matched answer is an observation, not a benchmark or proof of preserved behavior.

## Problems

Give the VS Code coding agent the exact terminal error and `docs/AI-HANDOFF.md`, not your API key. Ask it to fix the project and rerun the failing command. Report evidence accurately: installing dependencies, passing unit tests and rendering a browser are different checks.
